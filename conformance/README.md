# Conformance corpus for lossless JPEG (ITU-T T.81 Annex H, SOF₃)

1,707 frames: 1,691 that a conforming decoder must decode to stated pixels,
and 16 that it must refuse. Nothing here imports Plumbline unless you ask it
to, because the corpus is meant to be useful to projects that have never heard
of us.

```sh
python conformance/run.py                          # every decoder installed
python conformance/run.py --decoder plumbline
python conformance/run.py --decoder mypackage:decode_frame
```

Three outcomes, and the difference between the last two is the whole point:

| | |
|---|---|
| `exact` | the pixels match the expected values |
| `refused` | the decoder raised — allowed, and reported honestly as a gap |
| `WRONG` | the decoder returned pixels that are not the right pixels |

Only `WRONG` sets a non-zero exit status. A decoder that refuses a case is
telling the truth about its limits; a decoder that returns the wrong pixels is
not, and nobody downstream can tell.

## Where the expected pixels come from

Each valid case is built by **encoding an image we chose** (`encode.py`) and
asserting that it decodes back to that image. The expected values are the
input, not any decoder's output, so a disagreement is a fact rather than an
opinion.

That encoder exists because a frame with restart markers cannot be built out
of random bytes: a real encoder ends each interval by padding to a byte
boundary and emitting `RST0`–`RST7` in turn, and only whatever produced the
bits knows where that boundary falls. An earlier corpus here was generated
from random bytes, declared 114 of its 206 cases as failures of every other
decoder, and was wrong in all of them — the frames announced a restart
interval in the header and contained no `RSTn` at all. It was deleted rather
than published.

**The encoder is not part of the library and must never become part of it.**
Plumbline decodes and refuses to write files. A decoder that is wrong is
visible the moment somebody looks at the image; an encoder that is wrong
corrupts an archive silently, years before anybody opens it again.

## A round trip is not evidence

This is the lesson the corpus has now had to learn twice, and it is written
here because it is the failure this directory is most exposed to.

A corpus generated by your own encoder and checked by your own decoder passes
whenever the two share an assumption — including a wrong one. Twice, every
case passed and every case was wrong:

- the encoder took differences **modulo 2^P** where T.81 §H.1.2.1 says modulo
  2^16, so the published frames sat in the wrong residue class and only a
  decoder sharing the mistake could read them;
- the encoder and all three decoders applied the horizontal predictor Ra to
  the image's first line only, where §H.1.2.1 applies it to the first line **of
  every restart interval**.

Together those made 1,472 of 1,706 cases disagree with pylibjpeg — a corpus
declaring almost every other implementation wrong, which is the same alarm
that fired the first time and has the same usual cause. Both are fixed;
pylibjpeg now agrees on 1,690 of 1,707, and the 17 that remain are its own
gaps (11 point-transform cases it does not implement, 6 malformed frames it
accepts).

So the standing rule for anything added here:

- [x] intervals end with a real, byte-aligned `RSTn`, cycling `RST0`–`RST7`
- [x] expected pixels come from the source image, not from a decoder
- [x] **every valid case is confirmed by at least one decoder that shares no
      code with this project**, or carries a written argument citing the T.81
      clause that says why it should not

That last box went unticked while the corpus was published, and it is the one
that would have caught both bugs on the day they were written.

## What the valid cases sweep

Precision 2–16 × predictors 1–7 × 1–4 components × restart interval × content
pattern, plus point transform 1/2/4/8. Restart intervals are `0`, one row, two
rows, and one wider than the whole image — whole MCU-rows only, because T.81
§H.1.1 and table B.7 require Ri for the lossless processes to be an integer
multiple of the MCU in an MCU-row. Two rows earns its place because §H.1.2.1
gives Ra to the *first* line of an interval and not to every line, and no
one-row interval can tell those apart.

Content is chosen to exercise the predictor rather than to look like anything:
a flat image hides every predictor bug because every prediction is right; a
gradient separates predictors 1–4; noise reaches the corners of the Huffman
table; and extremes force the differences that wrap, which is where predictors
5–7 carry an error forward.

## What the malformed cases are for

The specification bounds what a *conforming* frame looks like. It does not
bound how firmware gets it wrong, and no amount of reading T.81 tells you.
What can be enumerated is the family a break belongs to — a truncated scan, a
restart interval declared and never emitted, a Huffman table over- or
under-subscribed, an interval that is not whole MCU-rows — and for those the
corpus asserts only that a decoder must not return an image. These have no
right answer, so any pixels at all are wrong pixels.

## Regenerating

```sh
python conformance/generate.py
```

Must be reproducible: same seeds, same frames, same hashes. A hash that moves
means the generator or the reference implementation changed behaviour, and
both are things somebody needs to look at rather than commit.
